## PR A — upstream/mcp-closed-session-refresh-v2

    commit cfa406320
    
    fix(mcp): skip dynamic tool refresh when session is closed or superseded
    
    A dynamic tools/list_changed refresh can be queued behind a shutdown or
    reconnect. _refresh_tools captured self.session before acquiring the RPC
    lock and called list_tools() unconditionally, so a queued refresh could
    run against a None session (AttributeError) or, after a reconnect, race
    a stale session's in-flight response into overwriting the registry that
    belongs to the new session.
    
    Resolve the session only after entering the RPC lock, skip the refresh
    entirely when it's None, and discard the paginated response if the
    session was replaced while the fetch was in flight.

## PR B — upstream/session-recents-index

    commit f6b9258ee
    
    feat(state): add sessions.last_active index and legacy trigram opt-out
    
    Two related storage improvements to hermes_state.py:
    
    1. sessions.last_active (schema v24): a denormalized, indexed column
       (idx_sessions_last_active) that list_sessions_rich's recents view can
       ORDER BY directly instead of computing "most recent activity per
       compression chain" via a recursive CTE over every candidate row on
       each call. The column is kept current by:
       - a SQL trigger pair (LAST_ACTIVE_REPAIR_TRIGGER_SQL) that propagates
         message timestamp updates and session started_at changes up through
         compression-continuation chains,
       - _touch_session_last_active (append_message / bulk insert) and
         _refresh_session_last_active (session create/end/reopen, message
         replace/clear, delete/prune/delete_empty, import) for the write
         paths that need an authoritative recompute rather than a monotonic
         touch.
       A v24 migration backfills the column for every existing session on
       next open. Read-only cross-profile DB handles (which never migrate)
       detect a missing physical column via _has_sessions_last_active and
       fall back to the original computed-subquery SELECT.
    
       Mixed-version-writer safety: the UPDATE-OF-timestamp trigger alone
       can't see a message INSERT/DELETE from a writer that doesn't call the
       Python-level touch/refresh helpers (a different process version
       sharing this state.db during a rolling upgrade, another language
       binding, a raw SQL script). Rather than adding AFTER INSERT/DELETE
       triggers on messages — which, given trigger firing order, would run
       their expensive recursive-CTE body on every single message write
       including the ones the Python helpers already handled correctly,
       defeating the point of the index — SessionDB now runs a cheap
       unconditional reconciliation on every open (_find_stale_last_active_
       session_ids): a single aggregate query comparing each session's own
       MAX(message.timestamp) against its stored last_active, returning
       nothing when every writer has kept up. Only sessions actually found
       stale pay for the chain-aware _refresh_session_last_active recompute.
       This mirrors the existing "heal NULL active rows unconditionally on
       every startup" pattern already in this file.
    
       Also fixed two destructive paths that deleted without refreshing
       affected compression ancestors (clear_messages, delete_empty_sessions
       — capturing ancestor ids before deletion, matching the pattern
       already used in delete_session/delete_sessions/prune_sessions), and
       the import flow (import_sessions attaches parent_session_id only
       after all messages are already inserted, so the per-message touch
       calls run before there's any chain to climb — the chain is now
       explicitly settled via _refresh_session_last_active once every
       parent edge is final, which also gives an empty imported session a
       real last_active instead of leaving it NULL).
    
    2. sessions.disable_fts_trigram (config-backed, env override
       HERMES_DISABLE_FTS_TRIGRAM): lets a legacy (pre-v23 inline-FTS)
       install skip recreating its heavyweight trigram index, which — unlike
       the v23 external-content trigram table — duplicates full message
       content including large tool-call payloads. The flag only affects
       legacy installs still awaiting `hermes sessions optimize-storage`;
       v23-shape databases always keep the compact trigram index regardless
       of the setting, and the explicit optimizer still backfills it for a
       disabled legacy DB once migrated. Config surface/docs for this flag
       are intentionally not part of this PR — flagging as deferred rather
       than adding a docs surface here.

## PR C — upstream/approval-temp-alias-fix

    commit b890378de
    
    fix(approval): recognize the raw temp-dir alias in verification cleanup
    
    _is_verification_artifact_cleanup() only matched the realpath()-resolved
    temp directory, so on systems where tempfile.gettempdir() returns a
    top-level alias (e.g. macOS's /tmp, which resolves to /private/tmp) a
    verification-script cleanup command using the literal, unresolved path
    was never recognized as safe.
    
    Accept the raw (non-realpath) operand as an alternative match, but only
    when the raw temp dir's parent is the filesystem root — the exemption
    stays narrow and a non-root symlinked temp dir (arbitrary directory
    symlink tricks) still requires the canonical realpath form.
    
    Added a regression test for the top-level-alias case; the existing
    symlinked_temp_dir_only_exempts_canonical_target test continues to pass
    unchanged, confirming non-root symlinks are unaffected.
